# Where we were wrong, and what we did about it

Written 2026-11-12 after a review of the whole project (PROJECT_NOTES.md, docs/results.md, the code). Each item is either **fixed**, **fixable** (a fix is known and would need its own rule; not done in this project), or **accepted** (a limit we state). Nothing here is new data; it collects what the notes already record.

## A. Measurement and method
| # | What was wrong or weak | Status |
|---|---|---|
| A1 | The dev set made us overconfident: 0/100 silent errors on Set A, then 4/100 on the first held-out set (Set B, FAIL). | **Fixed by process:** every decision since then uses a rule written before the run and a set not seen before. |
| A2 | The code checks were designed from the Set B errors, so their Set B number (1/100) was leaky. | **Fixed:** measured again on unseen Set C (1/100, 95% upper bound 4.7%). |
| A3 | Importance score v1 was shipped as the ranking without any test. When tested against the analyst, it was no better than sorting by amount (AUC 0.681 both). | **Fixed:** ordering v2 measured on 12 new days and adopted (top pick 11/12 vs 5.5). |
| A4 | On that round, amount alone did better than the adopted key (12/12). We kept the dev choice; switching on the test round would be tuning. Also I knew round 1's result before labeling round 2, which may have pulled my labels towards amount. | **Accepted**, stated. Amount-only as the order would need its own rule and a new round. |
| A5 | The adopted ordering puts long contracts first, but the duration field it relies on was never measured for accuracy (only amount and currency were). Counterparty origin and related party, used in the score, are also unmeasured. | **Measured 13 Nov** (50 Set C, bar ≤ 3): long contract 3/50 → kept; foreign counterparty 7/50 and related party 5/50 → their points removed from the score. The model misses these facts (never invents them). |
| A6 | One person built the system, labeled the gold data, wrote most questions and reviewed the answers. No second rater, no agreement number. | **Accepted**, stated. A second labeler on a sample would be the first step. |
| A7 | Test sets are small (100 / 48 / 20 / 18), so bounds are wide; the rerank was adopted exactly at its bar (17/20), and on dev it fixed and broke 5 each at rank 1. | **Accepted**, stated with the bounds. |
| A8 | Detail card v1 assumed analysts write tickers; 0/10 did, so it failed (5/10 routed). | **Fixed:** name table (router v2, 18/20) and the guided form. |
| A9 | Several things were tried and did not pass their bars: cited answers (v1, v3, v4), quantities on the card, text-pattern injection checks, the Matriks cross-check alone, the word-list scope guard, BM25 / hybrid, chunking. | **Accepted**, reported as results, not hidden. |
| A10 | "Straight-through rate 89%" was Set C at level 2, without the Matriks cross-check and the source judge that run live. | **Fixed in the docs 16 Nov:** the live figure is about 78-80% (Set D flagged 20-22%; 21-24% on its random 38). Set C and Set D are two systems and are not pooled. Stated 22 Nov (second outside review): that is above the 15% flag bar written for Set C; Set D's rule only reported the rate, so no decision was attached. Bringing it down would need its own rule (which layer flags most) and a new set. |
| A11 | Set D's "0/50, upper 5.8%" pooled a census stratum (12) with a random one (38). | **Fixed in the docs 16 Nov:** random stratum only, 0/38 (upper 7.6%) and 1/38 (11.9%). |

Whether the readings disagree as often there is unmeasured. | **Counted on 24 Nov**, report only (no decision): in the saved nightly lists of 15-23 Nov (6 lists, 10 items; no list on 17-19 Nov) `two_run_disagree` 0 and `run_error` 0 (`scripts/two_run_count.py`, not in this repository, see E4; a failed second call would also count). Too few items to say how often the readings disagree live. |

## B. The product
| # | What is wrong or weak | Status |
|---|---|---|
| B1 | In the chat, an out-of-scope question that names a company and a detail ("ASELS temettü ne kadar?") gets an unrelated disclosure card. Scope guard v2 (router intent `out_of_scope`) blocked 10/10 out-of-scope but also 29/185 earlier in-scope questions (bar 3) → off (13 Nov). | **Accepted** for the final: three guards failed their bars. v3 (19 Nov: router untouched, a separate judge only on the content paths) still blocked 28/185 earlier questions (bar 3), the same as v2: the small-model judge over-blocks wherever it sits. The guided form avoids it; in the demo, no such questions. |
| B2 | Relative periods: **fixed 13 Nov** for a fixed phrase table (exact 10/10, false period 1/5, wrong fires 0/9 on earlier questions); phrases outside the table ("önceki hafta", "son günlerde") are not read, and a word like "son"/"geçen" in another sense can still be read as a period (1/5). Two companies in one question → only the first; a counterparty's name can be taken as the company. | Periods **adopted** with stated limits; the other two **accepted**. The form takes one day. |
| B3 | The system rarely says "the data cannot answer this": unanswerable questions still get a list or a card. | **Accepted**; cited answers that abstain did not pass their bar. |
| B4 | Search's typical miss: right company, wrong disclosure (all 16 rank-1 misses on Set C). A card can therefore show the wrong disclosure of the right company. | **Accepted**, stated on every card ("the card belongs to the first hit; read the KAP text"). |
| B5 | `MONEY_RE` misses "ABD Doları" (10 of 81 Set B amounts), so some currency checks do not fire. | **Parser gap closed 15 Nov, no observed effect:** `amount_checks_v2.py` in the pipeline (ADOPT_V2 on Set D: 0 new flags, 0 catches, 0 false alarms on the 12 of 732 pool texts it can affect, and 0 on Set C twice). Other spellings ("US Doları", the long form) are still not read. **Not closed for `currency_unclear`** (a TL amount with a foreign amount in brackets, `analysis/rules.py`): it reads only USD, EUR, GBP and the symbols $, €, £, so "(… ABD Doları)" or "(… Avro)" in brackets does not trigger it (the rule is frozen as measured on Set C; found by an outside review on 24 Nov). v1 frozen; `score_silent` keeps v1 so old numbers stay comparable. |

| B5c | TL values use Matriks' `tcmb_ex_rt` borrowed from a nearby record (≤ 10 days). TCMB gap filling off. |
| B6 | Weekly themes: about half of the theme words are generic; clusters follow company templates more than sectors. | **Accepted**, stated on the page; desks use the Matriks sector label. |
| B7 | Prices are unadjusted; splits are guessed by a 22% jump rule. EFORC has no prices and no sector. | **Accepted**, stated. |
| B8 | Disclosure texts come from the Matriks test environment, amounts from prod; revenue uses Matriks' choice of balance sheet. | **Accepted**, stated; counts match prod. |
| B9 | The "source sentence" on a card is the first sentence that contains the extracted number (no currency or context match). 32/32 found on the saved lists; nobody checked that it is the right sentence. | **Measured 20 Nov** (`docs/source_sentence_rule.md`, census of 34 saved items): the shown sentence was the amount's source in 32/32 (95% upper bound on the wrong rate 8.9%) → `SOURCE_OK`. The card keeps the wording "the sentence where the amount appears" (no panel change was made). |
| B10 | smtp-mcp was measured on 12 chosen cases with an automated approval and a local Mailpit; one high `npm audit` finding (nodemailer) is accepted after reading its source code; the LLM never calls it. | **Accepted**, stated: the mechanism is shown, not a person's attention or adversarial coverage. |
| B11 | Related work (20 Nov, public pages): reporting in 2026 says some companies draft filings so that AI tools miss information. Our injection test covered instructions planted in the text, not drafting that hides or buries information. | **Accepted**, stated in the README limits; a test would need its own rule, new texts and labels. |
| B12 | The effect of an amount's position in a long text (beginning, middle, end) on extraction was not measured. | **Accepted**, stated; median text is 52 words, so most texts are short, but long ones exist. |
| B13 | Post-hoc, from the source-sentence labels (20 Nov; not planned in that rule, not a rate measurement): I marked 2 of the 34 saved items as a wrong extracted amount; 1 of the 2 carried a review flag, 1 did not, so one silent error was seen on the saved lists (live nightly lists and demo days). | **Reported**, not analysed further; the measured silent-error rate stays Set C 1/100 (upper 4.7%). Same order as Set C; a new rate needs its own rule and set. |
| B14 | One local model, no fallback model: if `gemma4:e4b` fails or returns invalid output, the disclosure is not read again by another model. | **By design** (22 Nov): it is never dropped; it comes back as `run_error` and goes to **kontrol et**. A fallback model would make that night's output unmeasured; in production it should be measured on its own, or its output always flagged and logged as a degraded run. |
| B15 | Outside review (22 Nov): which items enter "Önce bak" is decided by the v1 importance level (high = score ≥ 4, weights set by judgment) or a review flag; ordering v2 only orders items inside each group. | **Stated** (results, system card). Changing the group rule would need its own rule and measurement. |
| B16 | Outside review (22 Nov): a duration written in parts ("2 yıl 6 ay") counts as its longest part (2.0 years), not the sum, so "1 yıl 11 ay" is not a long contract (≥ 2 years). | **Accepted**, frozen with the measured score (long contract 3/50 errors on Set C); a fix needs a new rule. |

## C. Operations and our own process
| # | What went wrong | Status |
|---|---|---|
| C1 | Two pulls on 10 Nov and again on 11 Nov, against Matriks' one-pull-per-day rule (the job was resumed in the same block as other commands). | **Fixed in code:** `pull_guard` refuses a second pull on the same day; the resume command is given alone. |
| C2 | Nightly runs of 6-7 Nov failed on a DB lock; the first live morning list failed on a missing package in the deploy environment. | **Fixed:** lock logging and retries; `pip install` after every deploy pull; `deploy_check`. |
| C3 | Agent output with Matriks amounts was pasted into the chat with the assistant twice (10 Nov), against our data rule. On 22 Nov, desk e-mail screenshots were shown to the assistant before masking: Matriks sector names as desk names and the "Neden" (reason) lines, no amounts; only the masked image was committed. | **Fixed by habit:** only counts and short observations come back; screenshots of real data are masked before they are shared. |
| C4 | The assistant (Claude) gave wrong diagnoses twice on 12 Nov (name matching, review statistics) and once blocked a branch checkout with its own worktree. | **Fixed:** each corrected in the notes the same day; rule: reproduce before fixing, close own worktrees before handing over. |
| C5 | "Today" questions answered "no disclosures" before the night's collection. | **Fixed:** shows the last collected day with a note. |
| C6 | `panel.sources_for_items` reads the DB when a day page opens, without the 23:40-23:50 guard the chat context has. | **Fixed 19 Nov:** every GET route that reads the DB (day page, desks JSON, themes, form step 2 with a company) answers 503 "Gece toplama penceresi" during 23:40-23:50 and opens nothing; self-test covers 5 DB routes × 3 times in the window, 6 other routes, 3 times outside. |
| C7 | Independent review (19 Nov): the nightly job runs on one laptop; if the Mac is off at 23:43 that night is missed (happened 17 Nov). | **Accepted, stated.** launchd does not catch up; the next night's 3-day lookback collects the missed days, but no list is made for them, and the 07:30 desk e-mail then carries the last saved list. A firm would run it on an always-on server (ours cannot reach Matriks: network block, open question to Matriks). |
| C8 | Pilot pulls cost the forward test three sealed days (17 Nov Mac off, 18 Nov capital pilot, 19 Nov FDV pilot). | **By design, stated before each pull:** one pull per day is enforced in code (`pull_guard`), so a pilot pull skips that night; each skip was written into `docs/forward_test_rule.md` before any outcome existed. Note 7 (19 Nov) then ended the scored window with the 20 Nov list so it can be scored on 24 Nov: scored sealed weekdays 16 and 20 Nov; 21-25 Nov are still sealed but not scored. |
| C9 | Second outside review (22 Nov): the panel is for one person. The chat history and the last form answer are kept per process, not per user, and only the model call is locked; two people on one panel at the same time could see each other's answers. | **Accepted, stated.** The panel binds to this computer only. A firm would put it behind a login with one session per analyst. |

## D. Found by outside reviews (19 Nov: another AI read a project brief, not the code; 22 Nov: a second AI read the public copy; 24 Nov: a third AI ran the submitted repository)
| # | Point | Status |
|---|---|---|
| D1 | Indirect prompt injection through the chat: retrieved disclosure text reaches the agent. | **Limited by design, not measured:** the LLM only picks a tool and a ticker; every number, list and link in an answer comes from the database through code, and the guided form needs no free text. A hidden instruction can at most change which tool runs. No red-team test of this path. |
| D2 | "Held-out" sets share companies (35 of Set C's 59 companies are in Set B). | **Stated** in `docs/results.md` ("How to read"): held-out means unseen disclosures, not unseen companies; no disclosure is in two sets. |
| D3 | The forward test (now 2 scored sealed weekdays, 16 and 20 Nov, after Note 7; very few disclosures) cannot validate importance as a financial signal. | **Stated:** it is an anti-lookahead check of the live pipeline (the list is sealed before prices exist), scored once on 24 Nov: `TOO_FEW` (3 look-first, 3 other; seals intact); it is not an alpha claim. |
| D4 | One annotator; questions written with the text in view; the "blind choice" is the author's. | **Stated** in `docs/results.md`; wording "analyst's blind choice" corrected to "the author's blind choice" everywhere it was a claim. |
| D5 | Local web pages and secrets. | **Checked 19 Nov:** panel and kap-kart bind to 127.0.0.1; pasted / KAP text is HTML-escaped (self-tests); full git history has 0 committed `data/` files, 0 `.env`, 0 token-like strings. |
| D6 | 22 Nov: the panel did not check the `Host` header, so a malicious site using DNS rebinding could have read local pages; kap-kart had no `Origin` check and hung on a negative `Content-Length`. | **Fixed 22 Nov:** the panel answers only `127.0.0.1`, `localhost` and `panel` (the compose name n8n uses), on any port; kap-kart refuses another site's form and a bad `Content-Length`. Self-tests send real requests with good, bad and missing headers. |
| D7 | 22 Nov: `docker compose up --build` failed (the Dockerfile copied `PROJECT_NOTES.md` from the root after it moved to `docs/`); on sample data, a guided-form day with no disclosures crashed and the night window blocked pages. | **Fixed 22 Nov**, with self-tests for the empty day and the window switch. |
| D8 | 24 Nov: the panel accepts a POST with no `Origin` header (`web/app.py`, `origin_ok`) without looking at `Sec-Fetch-Site`. | **Accepted, not changed on submission day.** Current browsers send `Origin` on a POST from another site, and the `Host` check (D6) refuses other host names, so the gap is narrow; requests without `Origin` are mostly `curl` and n8n. | D9 | 24 Nov: data paths (`settings.path(...)`, for example `DB_PATH`) are fixed when a module is imported. | **Accepted.** `KAP_DATA_DIR` must be set before the first import; `main.py` does this, and the tests set the module attributes. | D11 | 24 Nov: `requirements.txt` is not the full installed set, though `pyproject.toml` said so, and it pins three packages the code does not import (`google-auth`, `pyasn1`, `pyasn1_modules`). | **Comment fixed 24 Nov; list not changed on submission day** (changing it would need a new clean install and Docker build). The tested installs (clean clone, Docker) used this file as it is. |
| D12 | 24 Nov: on sample data, topic search and the detail card answer "search index missing", because the sample does not build the index. | **Stated** in `sample/README.md` and on the page itself. The company brief says the same for its "similar earlier disclosures" part. |

## E. Architecture debt (version 1) and its status in version 2
In version 1 these were left alone, because changing them would have touched the nightly path or hash-checked code. Version 2 (23 Nov, the `kap_triage/` package; [`v1_to_v2_map.md`](v1_to_v2_map.md)) fixed E1 and E2 without changing any output: the panel pages and the morning lists of the sample data are byte-identical.

| # | What | Status |
|---|---|---|
| E1 | Six modules in `scripts/` have evaluation-style names, but live modules import them (some only in their self-tests): `eval_vs_matriks.py` (`norm_cur`, used by `pipeline.py` and `matriks_crosscheck.py`), `eval_retrieval.py` (`rag_index.py`), `route_eval.py` (`word_date`, `periods.py`), `score_silent.py`, `tcmb_check.py` (`importance.py`, rate fill off), `quantities.py` (`agent.py`, off). | **Fixed in version 2 (23 Nov).** The few functions live code used moved next to it (`norm_cur` into `analysis/rules.py`, `word_date` into `assistant/periods.py`, the vector helper into `assistant/search.py`); the six evaluation modules are not in version 2. In version 1 they stayed, because `source_check.py` was hash-checked by kap-kart and `pipeline.py` is on the nightly path. |
| E2 | `scripts/` is one flat folder, and modules import each other by bare name (`from parse_form import parse_form`); there is no package. | **Fixed in version 2 (23 Nov).** One package, `kap_triage/`, in four folders, with one entry point (`main.py`) used by launchd, Docker and the MCP client; modules import `kap_triage.<folder>.<module>`. |
| E3 | `agent.py` (~1,000 lines) and `panel.py` (~1,170 lines) are large; their self-tests are a large part of those lines. | **Partly fixed in version 2.** The self-tests moved to `tests/` (pytest), so `assistant/agent.py` is 816 lines and `web/panel.py` 1,003 lines after `ruff format` (24 Nov; about 660 and 780 before it, because the formatter splits long lines); the routes moved to `web/app.py` (FastAPI). The two files were not split further; each keeps its reading map at the top. |
| E4 | Rules and notes name measurement scripts as `scripts/...`. Those scripts are not in this repository (instructor, 21 Nov: as little test code as possible). | **Stated; partly answered 24 Nov:** the Set C result can be recounted from `evidence/set_c.jsonl` (`python main.py verify-results`; written by `evidence/export_set_c.py` in the private repository with the frozen scoring functions, totals checked equal). It shows the count and the bound, not that each error type is right (that needs the licensed texts and labels). The regex baselines on Set C (A 25/100, B 29/100 silent) have their own file, `evidence/regex_set_c.jsonl` (written by `evidence/export_regex.py`; both regexes were run again and gave the saved outputs, 100/100). Other sets (Set A, Set B, the dev and Set C search questions, the 3/200 false alarms) have no evidence file. Each rule file keeps its bar and its result, and a rule is never edited after it is committed; [`v1_to_v2_map.md`](v1_to_v2_map.md) says where each named file is in version 2. |

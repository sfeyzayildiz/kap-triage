# Where we were wrong, and what we did about it

Written 2026-11-12 after a review of the whole project (PROJECT_NOTES.md, docs/results.md, the code). Each item is either **fixed**, **fixable** (planned, with its own rule), or **accepted** (a limit we state). Nothing here is new data; it collects what the notes already record.

## A. Measurement and method
| # | What was wrong or weak | Status |
|---|---|---|
| A1 | The dev set made us overconfident: 0/100 silent errors on Set A, then 4/100 on the first held-out set (Set B, FAIL). | **Fixed by process:** every decision since then uses a rule written before the run and a set not seen before. |
| A2 | The code checks were designed from the Set B errors, so their Set B number (1/100) was leaky. | **Fixed:** measured again on unseen Set C (1/100, 95% upper bound 4.7%). |
| A3 | Importance score v1 was shipped as the ranking without any test. When tested against the analyst, it was no better than sorting by amount (AUC 0.681 both). | **Fixed:** ordering v2 measured on 12 new days and adopted (top pick 11/12 vs 5.5). |
| A4 | On that round, amount alone did better than the adopted key (12/12). We kept the dev choice; switching on the test round would be tuning. Also the analyst knew round 1's result before labeling round 2, which may have pulled her labels towards amount. | **Accepted**, stated. Amount-only as the order would need its own rule and a new round. |
| A5 | The adopted ordering puts long contracts first, but the duration field it relies on was never measured for accuracy (only amount and currency were). Counterparty origin and related party, used in the score, are also unmeasured. | **Measured 13 Nov** (50 Set C, bar ≤ 3): long contract 3/50 → kept; foreign counterparty 7/50 and related party 5/50 → their points removed from the score. The model misses these facts (never invents them). |
| A6 | One person built the system, labeled the gold data, wrote most questions and reviewed the answers. No second rater, no agreement number. | **Accepted**, stated. A second labeler on a sample would be the first step. |
| A7 | Test sets are small (100 / 48 / 20 / 18), so bounds are wide; the rerank was adopted exactly at its bar (17/20), and on dev it fixed and broke 5 each at rank 1. | **Accepted**, stated with the bounds. |
| A8 | Detail card v1 assumed analysts write tickers; 0/10 did, so it failed (5/10 routed). | **Fixed:** name table (router v2, 18/20) and the guided form. |
| A10 | "Straight-through rate 89%" was Set C at level 2, without the Matriks cross-check and the source judge that run live. | **Fixed in the docs 16 Nov:** the live figure is about 78-80% (Set D flagged 20-22%). Set C and Set D are two systems and are not pooled. |
| A11 | Set D's "0/50, upper 5.8%" pooled a census stratum (12) with a random one (38). | **Fixed in the docs 16 Nov:** random stratum only, 0/38 (upper 7.6%) and 1/38 (11.9%). |
| A12 | The two-run flag was measured with two separate processes of 50 texts; live it is a second pass in the same process on days with 1-2 disclosures. Whether the readings disagree as often there is unmeasured. | **Planned after 26 Nov** (with the forward-test scoring): count `two_run_disagree` in the nightly lists of 15-25 Nov, number only. |
| A9 | Several things were tried and did not pass their bars: cited answers (v1, v3, v4), quantities on the card, text-pattern injection checks, the Matriks cross-check alone, the word-list scope guard, BM25 / hybrid, chunking. | **Accepted**, reported as results, not hidden. |

## B. The product
| # | What is wrong or weak | Status |
|---|---|---|
| B1 | In the chat, an out-of-scope question that names a company and a detail ("ASELS temettü ne kadar?") gets an unrelated disclosure card. Scope guard v2 (router intent `out_of_scope`) blocked 10/10 out-of-scope but also 29/185 earlier in-scope questions (bar 3) → off (13 Nov). | **Accepted** for the final: three guards failed their bars. v3 (19 Nov: router untouched, a separate judge only on the content paths) still blocked 28/185 earlier questions (bar 3), the same as v2: the small-model judge over-blocks wherever it sits. The guided form avoids it; in the demo, no such questions. |
| B2 | Relative periods: **fixed 13 Nov** for a fixed phrase table (exact 10/10, false period 1/5, wrong fires 0/9 on earlier questions); phrases outside the table ("önceki hafta", "son günlerde") are not read, and a word like "son"/"geçen" in another sense can still be read as a period (1/5). Two companies in one question → only the first; a counterparty's name can be taken as the company. | Periods **adopted** with stated limits; the other two **accepted**. The form takes one day. |
| B3 | The system rarely says "the data cannot answer this": unanswerable questions still get a list or a card. | **Accepted**; cited answers that abstain did not pass their bar. |
| B4 | Search's typical miss: right company, wrong disclosure (all 16 rank-1 misses on Set C). A card can therefore show the wrong disclosure of the right company. | **Accepted**, stated on every card ("the card belongs to the first hit; read the KAP text"). |
| B5 | `MONEY_RE` misses "ABD Doları" (10 of 81 Set B amounts), so some currency checks do not fire. | **Parser gap closed 15 Nov, no observed effect:** `amount_checks_v2.py` in the pipeline (ADOPT_V2 on Set D: 0 new flags, 0 catches, 0 false alarms on the 12 of 732 pool texts it can affect, and 0 on Set C twice). No error was ever traced to this gap. Other spellings ("US Doları", the long form) are still not read. v1 frozen; `score_silent` keeps v1 so old numbers stay comparable. |
| B5c | TL values use Matriks' `tcmb_ex_rt` borrowed from a nearby record (≤ 10 days). Checked against TCMB (16 Nov, `docs/tcmb_rule.md`): within 0.5% for 972/1045 = 93.0% under Matriks' documented convention (previous day's closing rate), 87.4% under the same-day bulletin (the rule's primary reference, not Matriks' definition; Note 2 of the rule); median difference 0.16%; EUR differs in every year. The 1045 records share about 540 dates, so they are not independent. | **Accepted:** 0 importance-level changes on 83 FX amounts (rank order not measured); convention question goes to Matriks (feedback doc). TCMB gap filling off. |
| B5b | Live use, 12 Nov morning list (Feyza's review): 2/2 flagged disclosures had wrong extractions, both caught by the flag (none silent). Types: mixed currency / split amounts not read (importance 0); a TL revision where only the FX part was scored. | **Fixable** with B5 (same family); not changed from these two cases, a v2 must be measured on a new labeled set. |
| B9 | The "source sentence" on a card is the first sentence that contains the extracted number (no currency or context match). 32/32 found on the saved lists; nobody checked that it is the right sentence. | **Accepted**, stated: "the sentence where the amount appears", not the model's source. |
| B10 | smtp-mcp was measured on 12 chosen cases with an automated approval and a local Mailpit; one high `npm audit` finding (nodemailer) is accepted on a source reading; the LLM never calls it. | **Accepted**, stated: the mechanism is shown, not a person's attention or adversarial coverage. |
| B6 | Weekly themes: about half of the theme words are generic; clusters follow company templates more than sectors. | **Accepted**, stated on the page; desks use the Matriks sector label. |
| B7 | Prices are unadjusted; splits are guessed by a 22% jump rule. EFORC has no prices and no sector. | **Accepted**, stated. |
| B8 | Disclosure texts come from the Matriks test environment, amounts from prod; revenue uses Matriks' choice of balance sheet. | **Accepted**, stated; counts match prod. |

## C. Operations and our own process
| # | What went wrong | Status |
|---|---|---|
| C1 | Two pulls on 10 Nov and again on 11 Nov, against Matriks' one-pull-per-day rule (the job was resumed in the same block as other commands). | **Fixed in code:** `pull_guard` refuses a second pull on the same day; the resume command is given alone. |
| C2 | Nightly runs of 6-7 Nov failed on a DB lock; the first live morning list failed on a missing package in the deploy environment. | **Fixed:** lock logging and retries; `pip install` after every deploy pull; `deploy_check`. |
| C3 | Agent output with Matriks amounts was pasted into the chat with the assistant twice (10 Nov), against our data rule. | **Fixed by habit:** only counts and short observations come back. |
| C4 | The assistant (Claude) gave wrong diagnoses twice on 12 Nov (name matching, review statistics) and once blocked a branch checkout with its own worktree. | **Fixed:** each corrected in the notes the same day; rule: reproduce before fixing, close own worktrees before handing over. |
| C6 | `panel.sources_for_items` reads the DB when a day page opens, without the 23:40-23:50 guard the chat context has. | **Fixed 19 Nov:** every GET route that reads the DB (day page, desks JSON, themes, form step 2 with a company) answers 503 "Gece toplama penceresi" during 23:40-23:50 and opens nothing; self-test covers 5 DB routes × 3 times in the window, 6 other routes, 3 times outside. |
| C5 | "Today" questions answered "no disclosures" before the night's collection. | **Fixed:** shows the last collected day with a note. |
| C7 | Independent review (19 Nov): the nightly job runs on one laptop; if the Mac is off at 23:43 that night is missed (happened 17 Nov). | **Accepted, stated.** launchd does not catch up; the next night's 3-day lookback collects the missed days, but no list is made for them, and the 07:30 desk e-mail then carries the last saved list. A firm would run it on an always-on server (ours cannot reach Matriks: network block, open question to Matriks). |
| C8 | Pilot pulls cost the forward test three sealed days (17 Nov Mac off, 18 Nov capital pilot, 19 Nov FDV pilot). | **By design, stated before each pull:** one pull per day is enforced in code (`pull_guard`), so a pilot pull skips that night; each skip was written into `docs/forward_test_rule.md` before any outcome existed. Note 7 (19 Nov) then ended the scored window with the 20 Nov list so it can be scored on 24 Nov: scored sealed weekdays 16 and 20 Nov; 21-25 Nov are still sealed but not scored. |

## D. Found by an independent review (19 Nov; another AI read a project brief, not the code)
| # | Point | Status |
|---|---|---|
| D1 | Indirect prompt injection through the chat: retrieved disclosure text reaches the agent. | **Limited by design, not measured:** the LLM only picks a tool and a ticker; every number, list and link in an answer comes from the database through code, and the guided form needs no free text. A hidden instruction can at most change which tool runs. No red-team test of this path. |
| D2 | "Held-out" sets share companies (35 of Set C's 59 companies are in Set B). | **Stated** in `docs/results.md` ("How to read"): held-out means unseen disclosures, not unseen companies; no disclosure is in two sets. |
| D3 | The forward test (now 2 scored sealed weekdays, 16 and 20 Nov, after Note 7; very few disclosures) cannot validate importance as a financial signal. | **Stated:** it is an anti-lookahead check of the live pipeline (the list is sealed before prices exist), scored once on 24 Nov; the expected outcome is `TOO_FEW`; it is not an alpha claim. |
| D4 | One annotator; questions written with the text in view; the "blind choice" is the author's. | **Stated** in `docs/results.md`; wording "analyst's blind choice" corrected to "the author's blind choice" everywhere it was a claim. |
| D5 | Local web pages and secrets. | **Checked 19 Nov:** panel and kap-kart bind to 127.0.0.1; pasted / KAP text is HTML-escaped (self-tests); full git history has 0 committed `data/` files, 0 `.env`, 0 token-like strings. |
